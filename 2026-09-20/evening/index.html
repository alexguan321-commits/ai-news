第二层：架构选择揭示了 Anthropic 的真实战略

这个系统的架构选择值得深入分析：

1. 完全基于文件（Markdown + JSON），无构建步骤

这不是技术限制，这是战略选择。原因：

  • 金融行业 IT 部门极度保守，任何需要复杂构建流程的系统都会被否决
  • 文件级部署意味着合规审查可以在文件层面进行（"这个 Agent 的 skill 文件里写了什么？"）
  • 这意味着一个 MD 文件就可以被律师审阅——极大降低了合规摩擦

2. 双部署模式：Cowork Plugin + Managed Agents API

  • Cowork Plugin：面向个人银行家，直接安装在 Claude Cowork 环境中
  • Managed Agents API：面向机构，通过 `/v1/agents` 无头部署在客户自有工作流引擎后面

这个双模式设计说明 Anthropic 同时瞄准了个人用户（自下而上）和机构采购（自上而下）两条路径。

3. MCP 作为数据层的核心

12 个 MCP 连接器意味着 Anthropic 在押注 MCP 成为金融行业数据访问的标准协议。每个连接器都是一个数据源——Morningstar 的基金数据、S&P 的资本市场数据、Moody's 的信用评级数据、PitchBook 的 PE/VC 交易数据。

因果链： A（Anthropic 发布金融 Agent 套件）→ B（12 个 MCP 连接器覆盖金融数据全链条）→ C（MCP 成为金融数据访问的事实标准）→ D（其他 AI 公司被迫支持 MCP 才能进入金融行业）→ E（Anthropic 通过 MCP 生态锁定金融行业客户）

让我做一个具体的工作流分析。以一个典型的 IPO 尽职调查为例：

传统流程（2024年）： 1. 初级分析师（1-2人）花 3 天收集行业数据 → 从 S&P、FactSet、Bloomberg 手动下载 2. 花 2 天构建可比公司分析表 → Excel 手工操作 3. 花 1 天写 CIM（Confidential Information Memorandum）草稿 4. 花 1 天做 DCF 模型 5. VP 审阅，修改，再审阅 → 2 天 6. 总计：约 10-12 个工作日

效率提升：6-8 倍。

这意味着什么？意味着同样的工作量，只需要 1/6 到 1/8 的人力。

因果链： A（Agent 将投行工作流效率提升 6-8 倍）→ B（同样的交易量只需要 1/6 的分析师）→ C（投行不再需要大规模招聘初级分析师）→ D（MBA 毕业生的传统职业路径被打破）→ E（18 个月内，顶级商学院的金融行业就业数据将出现明显下滑）→ F（这会倒逼商学院重新设计课程，从"教你做 DCF"转向"教你管理 AI Agent 做 DCF"）

🟠 Browser Harness：让 LLM 拥有"自愈"能力的浏览器操控系统——17.6K Star 揭示了 Agent 基础设施的真正瓶颈不是模型能力，而是环境交互

🔗 来源：GitHub - browser-use/browser-harness

优先级：🟠 高优先级

大胆预判：12 个月内，"自愈型浏览器 Agent"会成为所有 AI Agent 平台的标配功能。18 个月内，Browser Harness 的架构模式（核心保护 + Agent 自写辅助函数）会成为 Agent 工具开发的行业标准。24 个月内，传统 RPA（机器人流程自动化）市场会被 Agent 浏览器操控吞噬 40% 的份额——UiPath 和 Automation Anywhere 的股价会因此下跌 25%。

核心创新：自愈架构

Browser Harness 的核心创新不是"让 LLM 控制浏览器"——这已经不新鲜了。核心创新是自愈机制： 


● Agent: 想要上传一个文件
  │
  ● Agent 检查 agent_helpers.py → 辅助函数不存在
  │
  ● Agent 自己编写辅助函数 → 保存到 agent_helpers.py
  │
  ✓ 文件上传成功
  │
  ● 下次遇到类似任务 → 直接复用已编写的辅助函数

这意味着：

  • Agent 每完成一个任务，系统就变得更强
  • 辅助函数是累积的——今天写的上传函数，明天可以直接用
  • 核心代码（`src/browser_harness/`）受保护，Agent 不能修改——这防止了 Agent 破坏系统本身

这个设计直接呼应了 Andrew Ng 在 Graph Engineering 课程中讲的核心原则："Verifier 必须是独立节点"。Browser Harness 把"核心系统"和"Agent 扩展"分离开来——核心系统保证基础能力，Agent 扩展提供增量能力，两者通过明确的边界隔离。

因果链分析

A（Browser Harness 实现自愈型浏览器操控）→ B（Agent 每完成一个任务就积累一个可复用的辅助函数）→ C（Agent 的能力随使用时间指数增长）→ D（传统 RPA 的"预定义流程"模式被"自适应流程"模式取代）→ E（RPA 市场在 24 个月内萎缩 40%）

与 LLM Wiki 知识关联

这与 9 月 18 日入库的 Graph Engineering 知识卡片高度相关。Mahax 的文章明确指出：

"What changed is only what a node means... Now a node can be be an agent that can do almost anything. Same graph, much more capable vertices."

Browser Harness 正是这个理念的实现——浏览器操控的"节点"从预定义的 Playwright 脚本变成了能自我进化的 Agent。而且它完美实践了"代码作为 Graph"模式：核心代码提供确定性框架，Agent 在框架内自主扩展。

策略建议

1. 如果你在构建 Agent 系统：立即研究 Browser Harness 的架构。关键学习是"核心保护 + Agent 自写扩展"模式——这个模式适用于任何 Agent 工具开发。 2. 如果你是 RPA 从业者：你必须在 12 个月内转型。传统 RPA 的"预定义流程"模式会被"自适应 Agent"模式取代。学习如何构建自愈型 Agent 系统。 3. 如果你是投资者：UiPath（PATH）和 Automation Anywhere 的估值逻辑正在被颠覆。建议在 Q4 前减持这两个标的。

🟠 Builder.io Agent-Native：当 Agent 不再"点击 UI"而是"共享 Action 层"——这可能是 Agentic App 的正确架构

🔗 来源：GitHub - BuilderIO/agent-native

优先级：🟠 高优先级

大胆预判：12 个月内，"Agent 通过 UI 点击来完成任务"的模式会被淘汰。18 个月内，"共享 Action 层"会成为所有 Agentic App 的标准架构。24 个月内，Builder.io 的 Agent-Native 框架会被至少 3 家 Fortune 500 公司采用来构建内部 Agent 应用。

核心创新：共享 Action 层

Builder.io 的 Agent-Native 框架提出了一个关键洞察：

"Coding agents work with more than a text box. Their environment provides context, tools, files, tests, and previews that make their capabilities and results visible. Knowledge work needs that same kind of environment."

当前的 Agent 系统有一个根本性问题：Agent 和 UI 是分离的。Agent 在后台工作，UI 展示结果。用户无法看到 Agent 在做什么，也无法干预 Agent 的决策过程。

Agent-Native 的解决方案是共享 Action 层：

1. 每个能力被定义一次为一个 Action 2. Agent 通过 Action 作为工具来工作 3. UI 通过同一个 Action 函数直接调用 4. Action 同时通过 HTTP、MCP、A2A 和 CLI 暴露

这意味着：

  • Agent 和 UI 使用完全相同的底层操作
  • 用户可以在 UI 中看到 Agent 正在执行的 Action
  • 用户可以随时接管 Agent 的工作（因为操作是相同的）
  • Agent 不会"点击按钮"——它调用的是和 UI 一样的 API

内置的 9 个 Agent 应用

Agent-Native 不是空架子——它自带了 9 个开源 Agent 应用：

应用 功能
Clips 录制和理解会议、屏幕、语音笔记
Design 生成和优化交互设计
Slides 创建和编辑品牌演示文稿
Analytics 数据问答和仪表板构建
Calendar 时间管理、日程安排、预约
Mail 邮件优先级、回复草稿、跟进
Assets 品牌媒体创建和组织
Content 内容起草、组织和发布
Plans 可视化计划创建（图表、线框图、原型）

因果链分析

A（Agent-Native 实现 Agent-UI 共享 Action 层）→ B（Agent 和人类使用完全相同的操作接口）→ C（用户可以随时观察和接管 Agent 工作）→ D（"黑箱 Agent"模式被淘汰）→ E（"透明 Agent"模式成为标准）→ F（企业客户对 Agent 的信任度大幅提升）→ G（Agent 在企业中的部署速度加快 3 倍）

策略建议

1. 如果你在构建 Agent 应用：立即研究 Agent-Native 的架构。"共享 Action 层"模式比"Agent 点击 UI"模式更可靠、更透明、更可维护。 2. 如果你是企业 IT 决策者：Agent-Native 的"自带 LLM、数据库、工具"理念意味着零供应商锁定。这是企业级 Agent 应用的正确采购策略。

关联 2：Browser Harness ↔ Loop Engineering 知识卡片

Andrew Ng 课程中讲到的"Loop Engineering"原则：

"Loop engineering is designing the system that prompts your agents."

Browser Harness 的自愈架构正是 Loop Engineering 的完美实现：

  • Agent 在工作中遇到新任务 → 编写辅助函数
  • 辅助函数被保存到 workspace → 下次复用
  • 系统随使用时间变得更强 → 这就是"Loop"的累积效应

关联 3：Agent-Native ↔ Self-Modifying Agents 知识卡片

Andrew Ng 课程中关于"Self-Modifying Agents"的安全原则：

"If an agent can rewrite code or configuration, its proposed change should not be the only evidence used to accept that change."

Agent-Native 的"共享 Action 层"设计天然满足这个安全原则：

  • Agent 通过 Action 层操作 → 所有操作都被 UI 可见
  • 用户可以随时观察 Agent 的行为
  • 用户可以随时接管和修改 Agent 的决策

被验证的预测： "透明 Agent"模式会比"黑箱 Agent"模式更受企业欢迎——Agent-Native 的设计选择验证了这一点。
