🔴 Graph Engineering完整课程：从Prompt到产品的隐藏层

核心洞察

Bun案例：

  • Bun用AI在11天内将535,000行Zig代码重写为100万+行Rust代码
  • 这相当于一个团队近一年的手工工作量
  • 生成的运行时（Bun v1.4.0）已经在你电脑上

关键洞察：

"You draw a line where the work is a graph."（工作本来是图，你却画了一条线）

6步构建你的第一个图

Step 1: 看到不存在的边（假边测试）

  • 对每个"然后"问：下一步是否真的读取了上一步的输出？
  • 是 = 真正的边，保持顺序；否 = 从未是边，同时运行

Step 2: 画出你的图

  • 遍历步骤，标记每个接缝：真正的边，还是不是
  • 找到最长的真正边链 = 关键路径

Step 3: 构建和运行你的第一个图

  • Claude Code实现：一行描述，让Claude写编排器
  • 四个阶段：Scope → Fan-out → Verify → Synthesize
  • 限制：16个Agent同时运行，每次运行1000个

Step 4: 让图变得强大

  • 新鲜上下文验证器：验证器是独立节点，有新鲜上下文
  • 隔离：将舰队分片到worktrees（仓库的独立工作副本）

Step 5: 瞄准舰队并计算胜利（Amdahl定律） 

S = 1 / ((1 − p) + p/N)
  p = 独立工作的份额（可并行）
  N = Agent数量

p = 0.95, N = 16  →  ×9.14   (不是×16)
p = 0.70, N = 16  →  ×2.91
ceiling (N = ∞)   =  1 / (1 − p)

Step 6: 本周你将构建的六个图

  • 安全扫描、引用研究、模块移植、对抗性diff审查、定时生态系统扫描、未知大小发现

关键洞察

"A prompter asks a question. An architect draws a graph."（Prompt工程师问问题，架构师画图）

三句话掌握整个学科：

  1. Fan out where the work is independent.（在独立工作处扇出）
  2. Gate the edges where confidence matters.（在信心重要的地方门控边）
  3. Freeze the nodes that hold the truth.（冻结持有真相的节点）

🔴 Master Agent Architecture：统一Harness、Loop、Graph三层架构

来源：marfin - X/Twitter 作者：marfin (@marfinxx, 2,341 followers) 互动：111 likes | 21 retweets | 8 replies | 32,829 views | 233 bookmarks 发布时间：2026-07-27

核心洞察

问题场景：

  • 大多数开发者像使用"昂贵的实习生"一样使用Claude Code和LLM Agent
  • 他们提供一个prompt，等待一个响应，然后手动检查接下来发生的事情
  • 其他团队陷入三种常见的失败模式：

1. 运行无尽的重试循环，烧掉数千美元而不检查代码是否编译 2. 在理解单个sub-agent如何工作之前，绘制巨大的50节点工作流图 3. 反复重写prompt，同时忽略底层环境

根本原因：

  • 这些方法失败是因为构建者将Harness Engineering、Loop Engineering和Graph Engineering视为竞争概念
  • 它们不是竞争的。它们形成单一生产系统的三个结构层

关键洞察：

"When builders isolate these layers, agents remain fragile demos. When engineers integrate all three into a single workflow, one prompt returns a verified, zero-defect production PR"

三层架构

1. Harness Layer（环境层）

  • 定义：模型外部的代码、配置、沙箱、git历史和内存
  • 职责：提供工作条件（执行shell命令、维护状态、检查文件系统、执行安全规则）
  • 核心组件：
  • CLAUDE.md系统规范
  • 7文件生产Harness结构
  • 状态哈希（防止Agent重复读取相同文件）

2. Loop Layer（反馈层）

  • 定义：模型调用后系统做什么：如何处理工具输出、评估证据、决定是否继续
  • 核心原则：循环基于证据，不是基于信心
  • 关键规则：
  • 不允许Agent循环直到它说"我完成了"（会导致幻觉补丁）
  • 循环必须要求确定性证据：通过的单元测试、零linter错误、schema验证

3. Graph Layer（流程层）

  • 定义：控制流：哪个节点接下来运行、工作在哪里分成并行任务、审批门在哪里
  • 核心能力：高并发扇出跨多个专业化sub-agent
  • 关键模式：异步并行扇出图

统一的5阶段Master架构

Stage 01: Harness Sandbox初始化

  • 锁定工作区权限
  • 加载仓库规则（CLAUDE.md）和进度文件
  • 激活工具结果缓存，防止冗余token消耗

Stage 02: 并行Graph扇出和范围界定

  • 根范围节点分析prompt
  • 将任务扇出到专业化sub-agent（文档搜索器、测试运行器、代码编写器）
  • 所有sub-agent并发执行

Stage 03: 本地证据门控重试循环

  • 每个节点运行内部验证循环
  • 代码修改触发自动化linter和测试命令
  • Sub-agent本地迭代，直到测试通过信号返回

Stage 04: Harness状态哈希和Token去重

  • Harness跟踪修改文件的状态哈希
  • 重复文件读取提供缓存状态哈希，零API延迟，零token成本

Stage 05: 对抗性红队门

  • Graph将完成的补丁路由到怀疑论者验证节点
  • 验证节点编写边缘案例测试以破坏补丁
  • 成功验证触发git commit并打开生产PR

失败诊断矩阵

系统失败源于误诊的层。使用这个矩阵识别哪一层需要修复：

问题 属于哪一层 修复方法
Agent丢失上下文或在turn之间读取错误文件 Harness 状态哈希、工具结果缓存
Agent输出损坏的代码但声称胜利 Loop 确定性证据循环、测试验证
工作顺序运行而不是并发 Graph 异步并行扇出、同步门

4大反模式

反模式1：基于信心循环

  • 依赖模型文本断言，而不是确定性测试通过信号
  • 修复：Loop层要求确定性证据

反模式2：嘈杂的Harness上下文

  • 将整个代码库转储到prompt上下文，而不是使用定向工具调用和状态缓存
  • 修复：Harness层使用状态哈希和缓存

反模式3：无约束的Graph循环

  • 构建重试路径，没有尝试限制或升级规则
  • 修复：Graph层添加尝试限制和升级规则

反模式4：将确定性工作强制放入模型

  • 使用LLM token进行字符串解析、去重或文件过滤，而不是简单的Python脚本
  • 修复：用Python脚本替代LLM

生产就绪检查清单

在部署Agent系统之前，验证这5个要求：

1. Harness：权限遵循最小权限、工作区在沙箱中运行、文件缓存激活 2. Loop：停止条件需要确定性测试证据、预算上限强制执行 3. Graph：独立任务并行执行、路由逻辑处理错误分支 4. Evaluation：真实执行trace自动重放以基准更新 5. Monitoring：成本、延迟、失败率、人工干预指标实时跟踪

性能基准：实习生模式 vs Master架构

实习生模式：

  • 一个prompt → 一个响应 → 手动检查
  • 高失败率、高token消耗、低可靠性

Master架构：

  • 一个prompt → 验证的、零缺陷的生产PR
  • 低失败率、优化的token消耗、高可靠性
