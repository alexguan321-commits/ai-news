第一层：Vibe Coding 的"生命周期"比任何人预期的都短

Andrej Karpathy 在 2025 年 2 月提出"Vibe Coding"概念时，他描述了一种"完全沉浸在氛围中、不看代码、只和 AI 对话就写出程序"的方式。当时这被视为一种解放——"人人都能编程"的终极形态。

但仅仅 18 个月后，HN 社区——全球最具影响力的技术社区——用 2700+ 分的集体投票宣告了这个实验的终结。

因果链： 1. 2025 年 2 月：Karpathy 提出 Vibe Coding → 被视为"编程的未来" 2. → 2025 年 Q2-Q3：大量开发者涌入 Vibe Coding → 初期兴奋期（"我不用学编程就能做产品了！"） 3. → 2025 年 Q4-2026 年 Q1：第一批"Vibe Coded"产品进入生产环境 → 问题开始暴露 4. → 2026 年 Q1-Q2：技术债务爆发 → 无法维护、无法调试、无法扩展 5. → 2026 年 Q3（现在）：集体反思 → "我回到手写代码了" 6. → 整个生命周期：约 18 个月——比大多数技术 hype cycle 都短

第二层：五篇文章代表了五种不同的"幻灭路径"

仔细分析这五篇文章，它们不是同质化的批评——每一篇都代表了一种不同的"从兴奋到幻灭"的路径：

1. "After two years of vibecoding, I'm back to writing by hand"（个人实践路径）

  • 作者花了两年时间认真实践 Vibe Coding
  • 最终发现：手写代码在长期可维护性、理解深度、调试效率上全面胜出
  • 关键洞察：Vibe Coding 的"爽感"是短期的，但技术债务是长期的
  • 865 分 = HN 社区对"长期实践者回归手写"的强烈认同

2. "The cult of vibe coding is dogfooding run amok"（文化批判路径）

  • Bram Cohen（BitTorrent 创始人）从文化角度批判 Vibe Coding
  • 核心论点：Vibe Coding 形成了一个"邪教"——盲目信仰、排斥批评、拒绝承认问题
  • "dogfooding run amok" = 过度自我验证导致的集体失明
  • 616 分 = 社区对"反邪教"叙事的强烈共鸣

3. "Breaking the spell of vibe coding"（认知觉醒路径）

  • fast.ai 的 Jeremy Howard 团队发文
  • 核心论点：Vibe Coding 是一种"认知魔咒"——它让你觉得自己很强大，实际上你在退步
  • 类比：就像计算器让你"不会心算了"，Vibe Coding 让你"不会写代码了"
  • 434 分 = 教育界对"AI 导致技能退化"的担忧

4. "Will vibe coding end like the maker movement?"（历史类比路径）

  • Technically 的分析师将 Vibe Coding 与 Maker Movement 对比
  • Maker Movement（2005-2015）也曾被预言为"人人都能制造"的革命
  • 最终结果：大多数 maker 项目停留在原型阶段，无法商业化
  • 预测：Vibe Coding 将走同样的路——"人人都能做产品"的泡沫将破裂
  • 405 分 + 439 条评论 = 社区对"历史重演"的激烈辩论

5. "Gas Town's agent patterns, design bottlenecks, and vibecoding at scale"（工程实践路径）

  • Maggie Appleton 的 Gas Town 项目深度复盘
  • 核心论点：在规模化场景下，Vibe Coding 的设计瓶颈暴露无遗
  • Agent patterns 的复杂性无法通过"vibe"来管理——需要严格的工程方法论
  • 403 分 = 工程界对"规模化挑战"的共鸣

第三层：这不是 Vibe Coding 的终结——而是"人机协作编程"的成熟

关键洞察：这五篇文章的标题都包含一个隐含的假设——"Vibe Coding 是一种独立的方法论"。但实际上，Vibe Coding 从来不是独立的方法论——它是"人机协作编程"光谱上的一个极端点。

让我用一个光谱来重新定位： 


完全手写 ←————————————————————→ 完全 Vibe
（传统编程）    人机协作编程     （AI 全写）
              ↑
         最优区域在这里

这五篇文章的真正贡献不是"杀死 Vibe Coding"，而是帮助行业找到了人机协作编程的最优区域——不是"完全手写"，也不是"完全 Vibe"，而是中间的某个位置。

因果链： 1. Vibe Coding 的极端（"完全不看代码"）被证明不可持续 → 行业向左移动 2. → 但"完全回到手写"也不是答案 → 行业不会回到 2024 年之前的状态 3. → 最优解在中间：用 AI 加速"重复性工作"（boilerplate、测试、文档），但保留人类对"核心逻辑"的理解和控制 4. → 这催生了一个新的编程范式："有意识的 AI 辅助编程"（Conscious AI-Assisted Programming） 5. → 与 Vibe Coding 的区别：开发者理解每一行代码，但用 AI 加速 80% 的"低认知负荷"工作

大胆预判

  • 3 个月内：GitHub 将推出"Vibe Coding 检测器"——自动标记"完全由 AI 生成、人类未审查"的代码库。企业将开始要求"代码人类审查证明"。
  • 6 个月内："Vibe Coding"将从一个正面词汇变成一个贬义词——类似于"nocode"在 2022 年后的命运。招聘 JD 中将出现"必须有手写代码经验，不接受纯 Vibe Coding 背景"。
  • 12 个月内：新的编程教育范式将出现——不是"学 Python"或"学 Vibe Coding"，而是"学人机协作编程"。课程将包含：何时用 AI、何时手写、如何审查 AI 输出、如何维护 AI 生成的代码。
  • 18 个月内：Vibe Coding 工具（如 Cursor、Replit Agent）将被迫转型——从"帮你写所有代码"变成"帮你写 80% 的代码，但确保你理解 100%"。这将是一个产品设计的根本性转变。
  • 24 个月内：行业将形成共识——"人机协作编程"是未来，但"协作"意味着人类必须保持理解能力。完全依赖 AI 的开发者将被视为"技术债务制造者"。

策略建议

  • 对开发者：立即开始建立"有意识的 AI 辅助编程"工作流。规则：(1) AI 可以写 boilerplate、测试、文档；(2) 核心业务逻辑必须手写或逐行审查；(3) 每周至少花 2 小时"纯手写"以保持技能；(4) 对 AI 生成的代码进行"理解测试"——如果你无法向同事解释某段代码为什么这样写，你不应该使用它。
  • 对团队负责人：在团队中建立"代码所有权"文化——每个人必须能解释自己负责的代码。禁止"这段代码是 AI 写的，我不确定它为什么这样工作"的情况。
  • 对投资人：Vibe Coding 赛道的估值将大幅下调。Cursor、Replit 等公司需要证明它们能转型为"人机协作"平台，而不是"替代人类"平台。关注那些定位在"最优区域"的新兴工具——它们帮助开发者"更快地理解代码"，而不是"更快地写代码"。
  • 对教育者：立即开始设计"人机协作编程"课程。核心模块：(1) AI 辅助编程的历史和局限；(2) 何时用 AI、何时手写；(3) AI 输出的审查和验证；(4) AI 生成代码的维护和调试。

深度分析：

这篇论文做了一个大胆的主张：Vibe Coding 不仅在个人层面不可持续，它在社区层面正在摧毁开源生态。

因果链： 1. Vibe Coding 让"发布项目"变得极其容易 → 开源项目数量爆炸 2. → 但 Vibe Coded 项目的维护者不理解自己的代码 → 无法回应 issue、无法修复 bug、无法审查 PR 3. → 结果：大量"僵尸项目"——发布了但无法维护 4. → 开源社区的"隐性契约"被打破：用户期望维护者会维护代码，但 Vibe Coder 没有这个能力或意愿 5. → 开源社区的信任被侵蚀 → "这个项目的维护者真的理解自己的代码吗？" 6. → 长期后果：开源社区的贡献者参与度下降，因为"和不懂代码的维护者合作"令人沮丧

这与"back to writing by hand"形成了完美的呼应：

  • 个人层面：Vibe Coding 导致"无法维护自己的代码"
  • 社区层面：Vibe Coding 导致"无法维护开源项目"
  • 两者是同一个问题的两个尺度

预测： 6 个月内，GitHub 将推出"维护者能力认证"——要求项目维护者证明他们理解自己的代码。12 个月内，开源许可证可能增加"维护责任条款"——如果你发布开源项目，你法律上有义务维护它。这将彻底改变"随便发布"的开源文化。
